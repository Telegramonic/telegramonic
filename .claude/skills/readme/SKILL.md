# README Standard Writing Guidelines

This skill defines the standards for creating, updating, and formatting README files across the Telegramonic repository. Maintaining clean, technically accurate, and easily readable documentation ensures developers and agents can quickly understand the system's architecture, dependencies, and entry points.

---

## 1. Core Principles

1. **Concise Prose**: Keep sentences tight, direct, and active. Avoid fluff and verbose descriptions. Let diagrams, code blocks, and tables do the heavy lifting.
2. **Visual Hierarchy**: Use Markdown headers (`#`, `##`, `###`), horizontal rules (`---`), and lists to structure information cleanly.
3. **No Placeholders**: Never include empty placeholders (e.g., `TODO`, `insert here`). Use concrete, working examples.
4. **Self-Documenting Code / Shell Commands**: Provide explicit commands rather than generic descriptions. Specify directories where commands must run.
5. **Interactive Diagrams**: Document complex interactions and system design visually using Mermaid diagrams rather than large walls of text.

---

## 2. Standard README Structure

Every major module or service README (such as `server/README.md` and `desktop/README.md`) should follow this structured sequence of sections:

### 1. Title & High-level Pitch

- Must start with a clear H1 representing the module name: `# Telegramonic [Module] (folder/)`
- A single concise paragraph summarizing what the component does, the core technologies used, and its role in the overall application.

### 2. Architectural Diagram

- A styled `mermaid` flowchart or sequence diagram depicting key components, data flow, HTTP/binary protocol bridges, and state boundaries.

### 3. Table of Contents

- A linked Markdown list pointing to all subsequent headers.

### 4. Directory Structure

- A clean ASCII tree diagram of the project folder. Key files and subfolders must have short, inline comments describing their role.
- Example:
  ```
  folder/
  ├── src/
  │   ├── main.rs          # Entry point and bootstrap
  │   └── config.rs        # App configuration schema
  ```

### 5. Tech Stack & Dependencies

- A markdown table listing primary crates/packages, versions, and specific purposes.
- Example:
  | Crate | Version | Purpose |
  |:---|:---|:---|
  | `axum` | 0.7.4 | Web framework and routing |

### 6. How It Works

- **Request Lifecycle**: An ordered list showing step-by-step how data moves through the component (e.g., client -> routing -> handler -> service -> data provider -> client).
- **Security & Middleware**: Description of request interceptors, authorization, session validation, or CORS policies.

### 7. Getting Started & Installation

- **Prerequisites**: Clear list of system level tools required (e.g., Rust stable toolchain, Node/Yarn version).
- **Step-by-step Commands**: Code blocks detailing how to install, build, run in dev mode, and run in production. Include commands from both monorepo root and directory levels.
- **Configuration Table**: A table detailing environment variables, descriptions, default values, and sample `.env` blocks.

### 8. API / Interface Reference

- For servers: A route summary table containing HTTP Method, Path, Authentication requirements, and Description.
- Detailed request & response blocks using formatted JSON or type signatures.
- Highlight serialization considerations (such as string-serialized `i64` variables to avoid JS precision loss).

### 9. Flow Guides (Auth, Upload, etc.)

- Flowcharts or ASCII sequence flows illustrating multi-step operations (e.g., 2FA authentication flow, chunked file upload lifecycle).

### 10. State Management & Persistence

- A table listing state variables, types, thread-safety wrapping (e.g., `Arc<Mutex<T>>`), and purpose.
- Documentation detailing persistent files generated by the runtime (e.g., session tokens, credential cache) and their gitignore status.

### 11. Testing Guide

- Commands for running unit and integration tests.
- A table showing test file coverage mapping.
- Description of test-router setups, mocks, and fixture utilities.

## 3. Formatting Standards

### Markdown Best Practices

- **Alerts**: Use GitHub-style warnings and notes to highlight critical information (e.g., session files being gitignored, simulated space capacities):
  > [!IMPORTANT]
  > API credentials must be submitted dynamically during the login flow; do not hardcode them.
- **Code Fences**: Always specify the language name for syntax highlighting (e.g., `rust`, `bash`, `env`, `json`, `mermaid`).
- **Tables**: Align header columns cleanly for readability. E.g., `|:---|:---|` for left-aligned columns.

### Mermaid Diagram Guidelines

- Use customized color classes for nodes to make diagrams visually distinct:
  ```mermaid
  classDef client fill:#eef2ff,stroke:#6366f1,stroke-width:2px,color:#1e1b4b;
  classDef server fill:#fdf2f8,stroke:#ec4899,stroke-width:2px,color:#500724;
  ```
- Always quote labels containing parentheses, brackets, or commas to avoid rendering errors. E.g., `node["Label Name (Detail)"]`.

## 4. Maintenance Rule

Whenever a source code modification introduces changes to:

1. Endpoints, routing paths, or payloads.
2. In-memory state keys or persistence directories.
3. Dependencies and tech stack versions.
4. CLI options or environment variables.
